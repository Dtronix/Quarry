## Security
| ID | Finding | Sev | Why It Matters |
|----|---------|-----|----------------|
| F6 | `FindDisallowedMethodCall` (`SnapshotCompiler.cs:240-256`) inspects only `InvocationExpressionSyntax`. Object-creation expressions execute arbitrary constructors when the recompiled `Build()` is invoked in-process (e.g. `new FileStream("x", FileMode.Create)` creates a file, `new System.Net.Sockets.TcpClient(host, port)` opens a connection), and property getters/setters are also unchecked. Matching is name-only, so any method *named* `Parse`/`Name`/`Build`/`Schema` on any type passes (e.g. `Enum.Parse`, `int.Parse`). Compilation references include the full user project reference set (`compilation.References`), so such types resolve. | M | Pre-existing gap, not widened by this change (the three added names — `DefaultValue`, `Collation`, `CharacterSet` — are all pure builder setters, and `Default` was removed). But this whitelist is the sole guard on in-process execution of recompiled user snapshot code, and the new coverage test now pins the whitelist as the contract — worth a separate hardening issue (validate object creations + symbol-based rather than name-based matching, or compile against a minimal reference set instead of `compilation.References`). |
| F7 | `AllowedMethods` visibility widened from `private` to `internal` for the coverage test, and it is a *mutable* static `HashSet<string>` (`SnapshotCompiler.cs:17`). Any code in Quarry.Tool (and Quarry.Tests via compile-include) can now mutate the security whitelist at runtime. | L | Low practical risk (no current mutators; single-run CLI), but a security-relevant set exposed wider than needed invites accidental or test-pollution mutation. `FrozenSet<string>`/`IReadOnlySet<string>` (or keeping the field private behind an internal read-only accessor) closes it cheaply. |

## Test Quality
| ID | Finding | Sev | Why It Matters |
|----|---------|-----|----------------|
| F8 | `CompileAndBuild_SnapshotFailsToCompile` (`SnapshotCompilerTests.cs:401`) passes for the wrong reason. Inside Quarry.Tests, `typeof(SchemaSnapshotBuilder).Assembly` at `SnapshotCompiler.cs:141` resolves to **Quarry.Generator.dll**, where the builders are `internal`, and the recompiled assembly ("QuarrySnapshotCompilation") is not an IVT target — so *every* snapshot, including a perfectly valid one, throws "failed to recompile" in the test harness (the workflow notes acknowledge this environment limitation). The test's `Length("not an int")` payload is irrelevant to its outcome, and the assertion checks only the message prefix, not that the diagnostics mention the actual error. Consequently `SnapshotCompiler.CompileAndBuild`'s success path has zero test coverage (the round-trip test covers generated-code-vs-runtime-builders, but not SnapshotCompiler's own reference wiring and `using Quarry.Migration;` → `Quarry.Shared.Migration` rewrite). | M | The test suite gives false confidence that the compile-failure path is specifically exercised. If the emit-failure branch regressed (e.g. to return null), the test catches it — that much is real — but a regression in reference assembly selection or the namespace rewrite would be invisible until a user runs the tool. At minimum assert the thrown diagnostics contain the expected error (e.g. arg-type mismatch text); better, make the shared-assembly reference injectable so a genuine success-path test is possible. |
| F9 | The command-level guards this fix installs are untested: `FindAndBuildSnapshot`'s throw-on-null (`MigrateCommands.cs:775`) and `MigrateScript`'s throw-instead-of-`-- ERROR` (`MigrateCommands.cs:485`) have no test — `MigrateCommands.cs` is not compile-included into Quarry.Tests, and the issue's work item 3 explicitly asked for a test "that a failed snapshot compile aborts `migrate add`". The plan quietly scoped this down to SnapshotCompiler-level tests. | M | The empty-baseline degradation lived precisely at this seam (null flowing into `SchemaDiffer.Diff`). If someone later "softens" `FindAndBuildSnapshot` back to nullable, no test fails. Compile-including MigrateCommands.cs (pattern already exists for BundleCommand/CommandHelpers) would allow a direct guard test. |
| F10 | `CreateFullFeaturedSnapshot` (`SnapshotRoundTripTests.cs:519`) uses an FK with *both* actions non-default (`Cascade`, `SetNull`); the mixed case — `OnDelete` default, `OnUpdate` non-default — is missing, and it is exactly the case where generation is wrong today (F4). Adding that FK would currently fail the round-trip test. | L | The round-trip test's stated purpose is "every builder feature"; this is the one semantic corner it misses. Should be added together with the F4 fix (it cannot be added before, as it would break the suite). |

Otherwise strong: the not-found→null, disallowed-method (message names the method), and whitelist-coverage tests all exercise the real production code paths (`FindDisallowedMethodCall` is tested both directly and through `CompileAndBuild`); the coverage guard reuses the production scanner on real generator output, which structurally pins whitelist ⊇ emissions; MigrationCompilerTests cover not-found/no-Upgrade/compile-fail/success including a real SQL assertion; the round-trip test asserts diff-empty in both directions plus persisted-hash equality, and correctly compiles against Quarry.dll per the design decision.
