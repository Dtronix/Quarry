| `UsageSiteDiscovery.IsPatchVariableReference` (`UsageSiteDiscovery.cs:2684-2701`) walks `member.DescendantNodes().OfType<VariableDeclaratorSyntax>()`. **It does not visit method parameters** — `Set(somePatchParameter)` where the param is declared as `User.Patch somePatchParameter` will return false → falls through to UpdateSetPoco → CS9144. The decision log explicitly calls out "fails soft on ambiguous shadowing" but `UsageSiteDiscoveryPatchTests` only tests the single-declarator happy path. | Low | Possibly missed test for ambiguous-shadowing path. |
| The empty-mask `InvalidOperationException` throw is emitted unconditionally on every terminal path that builds the SQL — including `ToDiagnostics()` (via `EmitCarrierPreamble → EmitCarrierSqlDispatch → EmitPatchSqlDispatch → EmitInlineSqlBuilder` at `TerminalEmitHelpers.cs:931`). ## Security
| Finding | Severity | Why It Matters |
| --- | --- | --- |
| `_PatchFragments` `Prefix` strings (`CarrierEmitter.cs:1413-1414`) come from `col.QuotedColumnName` (dialect-quoted via `PatchInfo.FormatColumnName` at IR construction) plus the literal `" = "`. No user input flows into the prefix; column names are sourced from the entity schema (compile-time C# code). Safe. | Info | No injection surface. |
| Runtime SQL assembly walks the static `_PatchFragments` array and only appends `__frag.Prefix` and a dialect-correct placeholder — no user-controllable string concatenation occurs at runtime. Mask bits gate the iteration. | Info | Safe. |
| `WriteColumnInfo.IsSensitive` is plumbed from `column.Modifiers.IsSensitive` through `PatchInfo.FromEntityInfo` (`PatchInfo.cs:70`). However `_BindPatchParams` does **not** branch on `col.IsSensitive` to gate `ParameterLog.BoundSensitive` (compare with insert path at `CarrierEmitter.cs:999-1000`). If a Patch is applied to a column flagged `IsSensitive`, the value will not be redacted in trace logs — but it also won't be logged at all (see Correctness finding above). Net effect: no leak via ParameterLog, but the sensitive flag carries through into the IR with no consumer. | Low | The redaction guarantee is preserved by omission, not by intent. Should be tightened with an explicit choice (either log with redaction, or document that Patch path skips ParameterLog). |
| Diagnostic SQL output contains the literal token `{__PATCH_SET__}` (visible in manifest fixtures, e.g. `quarry-manifest.sqlite.md:140`). Token contents are static literals; no parameter values appear in diagnostic SQL output for Patch chains. Sensitive-column values cannot leak via `.ToDiagnostics()` because the SET clause is never expanded at diagnostic time. | Info | Sensitive-data leakage via diagnostics is structurally blocked. |
| `IPatchFor<T>` marker (`IPatchFor.cs`) is `public interface` with a single type parameter; no methods, no fields. Cannot be implemented incorrectly to gain access. Generic constraint enforcement is purely compile-time. | Info | Safe. |
| `PatchAction<T>` (`PatchAction.cs`) — public `ref` delegate. Standard C# ref delegate; no risk surface beyond what `Action<T>` already exposes. | Info | Safe. |
| `UpdateBuilderPatchExtensions` (4 methods) each throw `InvalidOperationException` on direct call. Generator interceptors override these at compile time. If a user uses optimized-interceptors-off (CSharp interceptors namespace not configured), the throw fires with a clear message ("indicates a code generation bug") — same pattern as existing carrier-method DIMs. | Info | Safe. |
