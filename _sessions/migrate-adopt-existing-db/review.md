## Plan Compliance
| ID | Finding | Sev | Why It Matters |
|----|---------|-----|----------------|
| F1 | The plan's "coherent composition" narrative (adopt = `baseline --from-database` + ordinary `migrate add`) is not what ships. `MigrateAdopt` re-implements the v2 diff with `NormalizeForDiff` (MigrateCommands.cs:343-345) rather than reusing plain `MigrateAdd`, because it *has* to: `MigrateBaseline --from-database` embeds the **rich** DB snapshot as `[MigrationSnapshot]` (currentSnapshot at MigrateCommands.cs:187 → `GenerateSnapshotAttribute(currentSnapshot)` at :1161), and a subsequent plain `migrate add` (no `--from-database`) does NOT normalize (:64-66), so it would diff rich-DB-snapshot vs sparse-project-schema and reintroduce the exact spurious-`AlterColumn` asymmetry the CRITICAL discovery documents. The documented standalone mechanism ("once that snapshot exists, an ordinary migrate add … produces the rename migration") is buggy; only `adopt` is safe. | M | The "building blocks compose" claim in plan.md/llm-migrate.md is aspirational; a user who runs `baseline --from-database` then `migrate add` (the described path) gets spurious per-column alters, not a clean rename migration. |
| F2 | `MigrateAdopt` hard-codes `baselineVersion = latest+1`, `renameVersion = latest+2` (MigrateCommands.cs:307-308) and marks the baseline applied unconditionally. On a project that already has migrations 1..latest that are NOT applied to the target DB, adopt records latest+1 as applied while the earlier versions remain pending/unrun. | L | Documented as a "fresh-ish project" assumption in workflow.md focus hints, but there is no guard/warning when `latestVersion > 0`, so a non-fresh adopt can silently desync history. |
| F3 | `baseline`/`adopt` write checksum sentinel `"baseline"` (MigrateCommands.cs:233, :361) instead of a real `ComputeChecksum`. `StrictChecksums=true` will warn on every baselined/adopted migration. | L | Accepted limitation (squash-consistent, per Step deviations). Recorded, not a new defect. |
| F4 | `MigrateBaseline` / `MigrateAdopt` / the `--from-database` branch of `MigrateAdd`/`MigrateDiff` live in MigrateCommands.cs, which is not compiled into the test project — the command orchestration itself is never directly tested; coverage is by-composition (adapter, differ, DropGuard, history writer tested in isolation). | L | Documented (Step 5 deviation). The abort/version/guard *wiring* is unverified; see F9. |

## Correctness
| ID | Finding | Sev | Why It Matters |
|----|---------|-----|----------------|
| F5 | `NormalizeForDiff` clears `SchemaName` to null (DatabaseSchemaReader.cs:221), so every `DropColumn`/`DropTable` step fed to `DropGuard` has `SchemaName == null`. `DropGuard.FormatTable` (DropGuard.cs:73-80) then emits an unqualified `SELECT COUNT(*) FROM "table"`. For PostgreSQL/SqlServer tables in a non-default schema, that query targets the wrong table (via search_path) or throws — the data-loss guard either mis-counts or crashes. Fine for SQLite / public / dbo (the only tested cases). | M | This is the bundle's core safety feature; on multi-schema PG/SqlServer it can silently under-count (bypass the guard) or abort ungracefully. |
| F6 | `DropGuard` counts by the column name taken from the *patched* "from" snapshot. When a `--rename-map` target does not match the schema name, `ApplyForcedRenames` renames the snapshot column to the target, the normalized diff then emits `DropColumn <target>`, and `DropGuard.CountAsync` runs `... WHERE "<target>" IS NOT NULL` against the live DB — which still has the *original* column name. Result: an unhandled `DbException` instead of the intended graceful data-loss message. | M | A misconfigured rename-map turns the safety path into a crash; the guard's "abort with a clear list" contract is broken. |
| F7 | `RenameMap` has no validation: entries matching no column are silently dropped (a typo'd `users.usr_name=UserName` is ignored, so the column later drop+adds or blocks with no hint), and two entries mapping to the same target in one table produce a duplicate-named-column snapshot (`ApplyForcedRenames`, RenameMap.cs:160-186) with no error. | L | Silent no-op / invalid snapshot from user input; hard to diagnose. |
| F8 | `DetectCanonicalTableRenames` (SchemaDiffer.cs:315-338) emits `RenameTable` with `dropped.SchemaName` and no `oldSchemaName`, unlike `DetectTableRenames` which handles a schema (namespace) move (:179-192). A canonically-equal table whose schema also changed loses the schema-transfer step. | L | Edge case (canonical name equal but schema differs); a namespace move would be silently dropped from the migration. |

## Security
No concerns.

_All identifiers interpolated into row-count SQL are quoted via `SqlFormatting.QuoteIdentifier`, which escapes the quote char (SqlFormatting.cs:44-49); history writes are fully parameterized (`FormatParameter`/`GetParameterName`, MySQL positional order preserved); `EnsureHistoryTableAsync` interpolates only the constant table name. Connection strings are never echoed to stdout/stderr (only "--connection required" style messages)._
