## Plan Compliance

| ID | Finding | Sev | Why It Matters |
|---|---|---|---|
| F1 | Plan step 4 requires "Fall back to step 5's guard if the containing type is not nameable/accessible from the interceptor." No such check exists. `CarrierAnalyzer.cs:380` sets `thisIndirection` for every ClosureCapture-plus-field clause, and `CarrierEmitter.cs:473` then emits `internal extern static ref global::<ContainingType>` inside a `file sealed class` living in a *different* file (`*.Interceptors.*.g.cs`). | H | A chain in a `private` nested class (or any type not accessible from the generated file) now emits an accessor whose return type cannot be named there → CS0122/CS0050 build break. The pre-existing pure-`FieldCapture` path is immune because it only ever puts the type name inside an `[UnsafeAccessorType("…")]` *string*; putting it in a real type position is new and unguarded. |
| F2 | Plan step 6 demands "**runtime execution** tests for every row of the table above". `LambdaCaptureExecutionTests.cs` has no test for the `for`-body-local row or the `if`-block-local-alone row, and `LambdaCaptureScopeTests.cs:274-318` rejects only 3 of the 4 multi-scope shapes — the `for`-loop variant has no coverage at any level. | M | `for` was one of the two loop forms newly added to `IsOwnScopeStatement` (`DisplayClassNameResolver.cs:118-123`); it is now the only newly-claimed scope form with zero tests. The plan's own risk note says the suite is "necessary but not sufficient — only the runtime tests prove a prediction". |
| F3 | Plan step 7 asked llm.md to record "the scope rules … and the ground-truth tables". `src/Quarry.Generator/llm.md:222-234` presents the table as the authoritative rule set ("So: a scope is a `BlockSyntax`; a **parameter** resolves to …; and `foreach`/`for`/`using`/`switch`-section **declarations** own a scope"), but omits two forms that also own a display class and are *not* handled by the code — `catch` clause variables and `switch`-expression arm variables (see F6, F11). | M | The stated purpose of the table is "what makes the next break diagnosable". A table that reads as complete but silently excludes two mis-handled forms actively misleads the next reader into trusting a wrong prediction. |
| F4 | Plan step 7: "Where the separate pre-existing member-access-root bug blocks it, keep the named method and say so in the fixture `<remarks>`." All bodies were inlined and the rewritten `<remarks>` (`ConcurrencyTests.cs:28-41`) never mentions #338 or the member-access-root constraint. The inlined bodies only avoid it because they deconstruct (`var (Lite, _, _, _) = harnesses[index];`) before chaining. | L | The constraint that kept these bodies working is now invisible; a later simplification to `harnesses[index].Lite.Users()` reintroduces the #338 failure with nothing in the fixture explaining why the deconstruction is load-bearing. |

## Correctness

| ID | Finding | Sev | Why It Matters |
|---|---|---|---|
| F5 | The `<>4__this` hop accessor is deduplicated **per extraction plan**, not per carrier: `var emittedThisHops = new HashSet<string>();` is declared *inside* `foreach (var extractionPlan in info.ExtractionPlans)` at `CarrierEmitter.cs:461-464`, while the method name `ThisHopMethodName` (`CarrierEmitter.cs:379-380`) is keyed only on the containing type — no clause index, unlike `__ExtractVar_{name}_{clauseIndex}` at `CarrierAnalyzer.cs:392`. | H | Two clauses on the same chain that each mix an instance field with a local (e.g. `.Where(u => u.Id > _min && u.Name == name).Where(u => u.Id < _max && u.Name != name)`) emit `__ExtractThis_<Type>` twice with identical signatures → CS0111 duplicate member in generated code. The carrier-body dedup key (`extractor.DisplayClassName`, line 367) also differs from the declaration dedup key (`extractor.ThisIndirectionDisplayClass`, line 469), so the two sets can disagree. |
| F6 | `IsOwnScopeStatement` (`DisplayClassNameResolver.cs:118-123`) does not include catch clauses, and `FindDeclaringScope` walks a `CatchDeclarationSyntax` past `CatchClauseSyntax`/`TryStatementSyntax` into the block **enclosing the `try`**. Verified against emitted IL: `var minId = …; try { } catch (Exception ex) { var n = ex.Message; … }` with captures in both yields `_0 { minId }`, `_1 { ex }`, `_2 { n }` — `ex` owns its own display class. | H | Two failures. (a) A lambda capturing `ex` is predicted at the enclosing block's ordinal → `InvalidCastException` at execution, exactly the class of bug this branch exists to remove. (b) Worse, a clause capturing `ex` **and** a method-scope local resolves both to the same block, so `CountCaptureScopes` returns 1 and the new multi-scope guard does **not** fire — the guard's safety invariant is defeated for this shape and the build silently succeeds. |
| F7 | `CountCaptureScopes` got a "declaration outside the clause lambda" filter (`DisplayClassNameResolver.cs:229-231`) but `LookupClosureOrdinal` (`DisplayClassNameResolver.cs:244-263`) — which picks the display class actually emitted — did not; it still returns on the **first** `CapturedInside` entry of any kind. Confirmed with Roslyn that for `u => u.Orders.Any(o => o.Items.Any(i => … o …))` the clause's `CapturedInside` does contain the inner lambda parameter `o`. | M | For a clause that mixes a nested subquery (whose inner parameter is captured) with a genuine outer capture, the ordinal can be taken from the inner lambda's scope while `CapturedScopeCount` reports 1 — so the guard certifies the site as single-scope and a wrong display class is emitted anyway. The two functions now encode contradictory notions of "the scopes this clause reads from" with no shared helper. |
| F8 | The `<>4__this` indirection is applied only in the parameter loop (`CarrierAnalyzer.cs:376-390`). The second `UpdateSetAction` pass over `SetActionAllCapturedIdentifiers` (`CarrierAnalyzer.cs:405-445`) still emits `effectiveCaptureKind = FieldCapture` with `effectiveDisplayClass = containingClass` (line 425-429) and no hop. | M | `Set(u => u.Name = _prefix + name)` — an instance field inside a computed Set expression alongside a captured local — still passes the display-class instance to an accessor typed for the containing class → `InvalidCastException` at execution. Step 4's stated behaviour ("when a clause lambda captures both an instance field and a local") is only half implemented, and no test covers this path. |
| F9 | `ToCSharpTypeName` (`CarrierEmitter.cs:400`) writes the containing-type display string straight into a `ref` return position. The name comes from `SymbolDisplayTypeQualificationStyle.NameAndContainingTypesAndNamespaces` (`DisplayClassEnricher.cs:182-184`), which renders a generic type as `Ns.Repo<T>`. | M | A chain inside a generic class with a field+local capture emits `ref global::Ns.Repo<T>` in a file-scoped carrier where `T` is unbound → CS0246, and the paired `[UnsafeAccessorType("Ns.Repo<T>+<>c__DisplayClass…")]` string is not a valid metadata name either. Nothing detects or guards this. |
| F10 | `SanitizeIdentifier` (`CarrierEmitter.cs:388-394`) maps every non-alphanumeric character to `_`, so it is not injective: `Ns.A_B` and `Ns.A.B` both yield `Ns_A_B`. | L | Two distinct containing types in one carrier collapse to the same `__ExtractThis_…` / `__self_…` name — a second route to the F5 duplicate-member break, and to a hop local silently bound to the wrong instance. |
| F11 | `switch`-expression arm variables are unhandled. Verified: `o switch { string s => (() => s.Length)() , … }` emits its own `<>c__DisplayClass2_1` whose field is named **`<s>5__2`**, not `s`. `FindDeclaringScope` resolves the arm variable to the enclosing block. | L | Both the ordinal *and* the `[UnsafeAccessor(Name = "s")]` field name would be wrong, so this shape fails at execution with no build-time signal. Low likelihood inside a Quarry clause, but it is a second unhandled own-scope form beyond F6. |
| F12 | When the `+<>c__DisplayClass` marker is absent, `CarrierAnalyzer.cs:384-389` leaves `thisIndirection` null and falls through to emitting a field-named extractor against the *display class* — the exact `MissingFieldException` shape this change exists to remove — with no diagnostic. Same silent fall-through at lines 369-374. | L | Unreachable by construction today (the enricher always builds the name with the marker), but it degrades silently rather than failing loudly, against this repo's stated preference elsewhere (e.g. the fail-loud bound checks in `DisplayClassEnricher.cs:117-136`). |
| F13 | `CapturedScopeCount` defaults to `0` and is only assigned at the end of the enrichment loop (`DisplayClassEnricher.cs:216-220`). Every `continue` earlier in that loop (missing syntax tree at :113, span out of range at :122, recovery mismatch at :131, no enclosing method at :154, `methodOrdinal < 0` at :177) leaves it at 0. | L | "Never analysed" is indistinguishable from "captures from exactly one scope", so the guard silently does not fire on sites whose enrichment was skipped. An `int?` / `-1` sentinel would make the unanalysed case explicit. |
