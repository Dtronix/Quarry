## Correctness
| ID | Finding | Sev | Why It Matters |
|----|---------|-----|----------------|
| F3 | A fully-represented final-else cascade nested inside an outer conditional arm still produces an unenumerated reachable mask — and the new validator cannot see it. Shape: `if (a) { if (b) q = q.Where(X); else q = q.Where(Y); } await q.Exec();` (also `if (a) { q = f ? q.Where(X) : q.Where(Y); }` and the dangling-else `if (a) if (b) X; else Y;`). Both sites sit at cascade depth 2 (allowed; `ChainAnalyzer.cs:636` demotes only > 2), group solely by the INNER cascade (`GroupKey`), and since the inner cascade has a final else with all arms represented, `EnumerateMaskCombinations` (`ChainAnalyzer.cs:2725-2726`) adds no 0 option → masks {1,2}. At runtime `a == false` sets no bits → Mask 0 → `ThrowHelper.UnenumeratedMask` throws an InvalidOperationException telling the user to file a generator-defect issue. `ValidateMaskEnumeration` is blind to this because `BuildCascadeShapes` (`ChainAnalyzer.cs:2743-2762`) derives `ZeroAllowed = !hasFinalElse \|\| armBits.Count < armCount` from the same innermost-cascade data — it never accounts for the cascade itself being conditionally entered (NestingDepth > 1 relative). The generator llm.md claim "Nested cascades enumerate independently (a reachable superset)" (`src/Quarry.Generator/llm.md:126`) is false for this shape. Pre-existing mis-enumeration class (old code produced the same {1,2}), so the branch improves the failure mode from null-CommandText provider crash to an actionable throw — but this is exactly the defect-2 class #307 set out to close, the shape is within documented limits (depth ≤ 2), and there is zero compile-time signal. Fix direction: force the 0 option (and `ZeroAllowed`) whenever the cascade's relative depth > 1, or intersect nested cascades' reachability. | H | Valid, documented-supported user code compiles silently and then reliably throws at runtime whenever the outer branch is not taken; the defense-in-depth validator shares the blind spot by construction. |
| F4 | Sites inside a NON-head arm's condition expression are now treated as unconditional. `DetectNestingContext` (`UsageSiteDiscovery.cs:2020-2027`) passes through when `prev` is neither the then-statement nor a final-else clause — including a site inside an `else if (...)` condition (e.g. `if (a) {...} else if ((q = q.Where(f)) != null) {...}`). That condition executes only when `a` is false, so the Where interceptor may never run, yet its predicate is baked into every variant and its carrier-bound parameters stay at defaults → silent wrong results. Old code counted such sites conditional (every `IfStatementSyntax` ancestor incremented depth), so this is a behavior regression, albeit for a contrived shape. Head-if conditions (always evaluated) are correctly unconditional. | M | Silent wrong SQL/parameters for a compilable shape; regression relative to master, though the shape (chain reassignment inside an else-if condition) is rare. Consider demoting condition-position sites in non-head arms to QRY032 instead. |
| F5 | Conditional Limit exposes new instances of the pre-existing bare-OFFSET bug: with an unconditional `Offset` and a conditional `Limit` (`q = q.Offset(5); if (f) q = q.Limit(10);`), the limit-inactive variant renders `FormatPagination(dialect, null, 5)` → bare `OFFSET 5` (`SqlAssembler.cs:1100-1110`), which SQLite/MySQL reject at runtime. Working Notes track offset-only pagination as a pre-existing separate-issue candidate, but that framing covers only chains that never had a LIMIT — mask gating now manufactures offset-only VARIANTS from chains that always specify one. | M | A chain that works when the branch is taken fails with a SQL syntax error when it isn't — same silent-compile/runtime-failure class as the defects being fixed. The follow-up issue must cover the variant-induced case, or `AppendPagination` should suppress OFFSET (or force demotion) when LIMIT is inactive on affected dialects. |
| F6 | The `relativeDepth <= 0` baseline subtraction (`ChainAnalyzer.cs:631-633`) still assumes a clause site at the terminal's depth shares the terminal's ARM. In `if (a) { q = q.Where(X); await q.Exec(); } else { q = q.Where(Y); }`, Y is depth 1 == baseline → treated unconditional → predicate baked into the executed SQL even though Y's interceptor never ran when `a` is true. Pre-existing (old code identical), but the branch reworked this exact loop and the new `GroupKey`/`ArmIndex` data is sufficient to detect terminal-vs-site arm divergence now. | L | Silent wrong results for a degenerate shape (clause after the terminal's arm is dead code anyway); worth a follow-up issue rather than this branch. |

## Security
No concerns. No user source text flows unescaped into generated code (clause fragments and paths go through `InterceptorCodeGenerator.EscapeStringLiteral`; the new emitted constructs use only integer bit indices and class names); `GroupKey` is generator-internal; `ThrowHelper.UnenumeratedMask` interpolates only the int mask; SQL variants contain only translated predicates as before. Condition text reaching manifest markdown labels is pre-existing behavior (see F12 for a cosmetic edge).

## Codebase Consistency
| ID | Finding | Sev | Why It Matters |
|----|---------|-----|----------------|
| F11 | The known-accepted `BuildCascadeShapes` vs `EnumerateMaskCombinations` duplication is faithful — armBits (SortedDictionary OR), armCount/hasFinalElse from sites, and zeroAllowed vs the 0-option condition are semantically identical. But that faithfulness is exactly why F3 escapes both: only the mask-SET construction is independent; the cascade-SHAPE derivation is shared logic written twice. Deriving `ZeroAllowed` in the validator from independent evidence (e.g. `NestingContext.NestingDepth` of the group's sites) would restore genuine defense-in-depth. | L | The "one bug cannot hide in both" doc claim (ChainAnalyzer.cs:2765-2768, llm.md) overstates the independence actually achieved. |
| F12 | Manifest variant labels (known, pre-flagged): the final else arm inherits the preceding else-if's condition text (both label "+b"), multi-clause arms emit duplicated labels ("+strict, +strict"), and a multi-line condition would break the `-- +label` comment line inside the fenced SQL block. `BuildBitIndexToConditionText` maps per-bit `ConditionText`, not per-arm identity, even though `ArmIndex`/`HasFinalElse` are now available. | L | Cosmetic-only (SQL is correct); Working Notes already nominate it as a REVIEW polish item — an "else"/arm-index label would fix all three. |
| F13 | The pagination `DiagnosticParameter` entries nested inside `ClauseDiagnostic` (`TerminalEmitHelpers.cs:419,422,431,434`) omit the `isConditional`/`conditionalBitIndex` metadata that the top-level `__params` entries now carry via `FormatPaginationMeta` (`:211`). | L | Minor internal inconsistency; the enclosing ClauseDiagnostic carries `isActive`/bit info, so consumers aren't misled, but the two surfaces should agree. |
